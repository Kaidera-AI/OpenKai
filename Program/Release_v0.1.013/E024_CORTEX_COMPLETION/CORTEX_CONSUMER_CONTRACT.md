# OpenKai ↔ Cortex consumer contract — the harness side (answer to `77db176e`, 2026-09-04)

Owner: kai@openkai. Status: OpenKai's binding statement of what the harness needs from Cortex v0.1.001 (KOS design 30, Wave E). Grounded in exact OpenKai 0.1.13 candidate `db7f921658c57e943a763a06bf25312d9ac5eef4` (`packages/coding-agent/src/openkai/cortex/*`, `memory-backend/cortex-backend.ts`, `cortex-ingest/*`); numbers and surfaces marked *proposed* are future requirements, while the host-B items explicitly marked adopted are present in this candidate.

**Authoritative host-B amendment (2026-09-04):** On the observed appliance, `POST /memory` persists a row immediately and a following `POST /search` can find it lexically. The row is not vector-recallable until the Cortex maintenance beat or an administrator backfill enriches it. Cortex globally upserts by `source`, so a retry of the same logical memory reuses its deterministic source while distinct logical contents use distinct sources. Embedding health must fail loudly from `GET /workers/health` and the administrator backlog; an empty `GET /degradation` response alone is not proof of embedding health.

## A · Lifecycle hooks: what the harness does, what it needs

Common rules for every hook: Cortex is **opt-in** (`memory.backend = cortex` or the managed `CORTEX_PROJECT` lane); every write carries a **roster writer** (explicit `cortex.agent`/`OPENKAI_AGENT`, else the project's registered `default_agent`; no writer ⇒ refused before any payload); user-controlled task, message, memory, degradation, and user-visible error content passes through `redactSecrets`. Automatic hooks never fail a turn: Cortex absent or degraded becomes "no memory this turn" with an honest status line. Explicit memory tools return an actionable error rather than silently succeeding.

**Retryable vs terminal, as OpenKai classifies today:** `409` on ingest = delivered; any `4xx` = configuration/contract error, surfaced, never retried; `5xx`, connection refused, timeout = transient, retried only where the table says. **Proposed for v0.1.001:** a `Retry-After` on 429/503 that the client honours, and `410 operation_id_expired` treated as terminal-success-unknown (re-issue with a new id, never replay).

**Authoritative health and configuration surfaces:** `GET /admin/cortex/config` identifies the provider/model actually seeded in the appliance. `GET /workers/health` supplies `workers.embed.ok`, and administrator `GET /beat/embeddings/backlog` supplies `backlog.total`; these are the fail-loud embedding-health signals OpenKai consumes. `/health` model fields are descriptive, and `GET /degradation` items remain supplementary and are rendered in redacted serialized form, but an empty degradation list does not prove that the embedding worker is healthy, the backlog is drained, or a selected model is servable. A future `capabilities` object on `/.well-known/cortex` may improve discovery but must not replace these checks.

## B · Endpoints OpenKai will call

**Historical 0.1.12 baseline (frozen behaviour, keep working):** `GET /health`, `GET /projects/{key}`, `GET /sessions/ingested-ids`, `POST /search` (`query`, `top_k`), `POST /memory` (`section`, `content`, `category`, `source`), `POST /sessions/ingest`, `GET /degradation`, `PATCH /admin/cortex/config` (admin token), `GET/POST /skills`, `DELETE /skills/{slug}`, `POST /skills/{slug}/bind`, `GET /events` (SSE). Headers: `X-Project`, `X-Agent-Name`, optional `Authorization: Bearer`.

**Adoption split:** exact OpenKai 0.1.13 candidate `db7f921658c57e943a763a06bf25312d9ac5eef4` adopts items 1–4 from the host-B amendment. Items 5–10 remain proposed W3c work and may begin only after Cortex publishes the versioned contract (P1), the joint plan is approved (P2), and that separate client delta is reviewed; they are not part of 0.1.13.
1. `GET /admin/cortex/config` (admin) — discover only the provider/model configuration actually seeded in the appliance; the picker must not synthesize alternatives.
2. `GET /workers/health` — consume `workers.embed.ok` as the worker fail-loud surface.
3. `GET /beat/embeddings/backlog` (admin) — consume `backlog.total` as the enrichment-progress fail-loud surface.
4. `POST /beat/embeddings/backfill` (admin) with `{table:"all", limit:1, dry_run:true, async_job:false}` — verify the current/applied embedding configuration before claiming it live.
5. `GET /.well-known/cortex` + `capabilities`/API revision — supplementary discovery for the status row and settings tab, never a substitute for items 1–4.
6. `POST /search` optional params: `filters` (type, tag, agent, since/until), `include` (source_facts, scores), `trace` (only under `/memory diagnose`), `as_of`, `prefer_observations` — first-turn recall and the new pre-compaction recall.
7. `POST /operations` (+ `GET /operations/{id}`, `retry`, `cancel`) for stop-time retention with caller `operation_id` idempotency — replaces client-side retry.
8. `POST /reflect` (structured answer with validated citations) behind a `cortex_reflect` tool — opt-in, discoverable.
9. Mental models + directives read path — the session-start seed (render budget ≤ 1,500 tokens); curation stays an operator surface (`/cortex` verbs), never a model tool.
10. Memory profile (`GET …/profile`: budgets/egress) — shown in `/cortex status`; not written by OpenKai.
Visibility (agent-private vs team) becomes a settings row only once Wave D lands; default team.
